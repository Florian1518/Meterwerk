The internal important-record condition was true in all five captured
comparisons. It was not the blocker in this reproduction. During startup,
`CheckArchiveTimeout()` returns while recovery is active, and the main loop
only caps its sleep by `archive_timeout` when recovery is inactive. The first
sleep therefore used 300 seconds. The later SQL probe reporting recovery=false
does not retroactively shorten that already-running wait. After waking, the
checkpointer invoked `RequestXLogSwitch(true)` and subsequent intervals were
approximately 60 seconds. See the original
[PostgreSQL source](https://github.com/postgres/postgres/blob/7d3e000c5961a544302072058a1184e9a588837b/src/backend/postmaster/checkpointer.c).

This directly establishes the startup-wait mechanism in the instrumented
reproduction and explains why 118–241 second observation windows can end
without a switch. Earlier runs lacking internal capture cannot individually
be assigned that cause with the same certainty.
